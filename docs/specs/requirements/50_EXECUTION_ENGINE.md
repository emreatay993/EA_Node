# Execution Engine Requirements

## Runtime Structure
- `REQ-EXEC-001`: the execution engine shall run workflows through `CorexRuntime`, with the QML shell as one client. `CorexRuntime` shall dispatch through `ExecutionBackendClient`, which pins one selected process, external-Python, or trusted in-process transport for each accepted run; process and external routes retain dedicated worker boundaries. Secure remote execution is a separate planned dispatch scope under `REQ-EXEC-020`; it does not widen this requirement or its existing proof.
- `REQ-EXEC-002`: the worker boundary shall use typed command/event payloads that round-trip through queue-safe dictionary adapters. Remote transport, negotiation, and trust are separate planned scopes under `REQ-EXEC-020` and `REQ-INT-018`; they do not widen this requirement or its existing proof.
- `REQ-EXEC-003`: runtime clients shall receive execution events without blocking the worker. `CorexRuntime` shall validate events, apply solution-store acceptance, and enrich accepted settlements before publication. Shell composition shall retain exactly one `Qt.QueuedConnection` from `ShellWindow.execution_event` to `RunEventController`; that controller shall route run state through `RunProjectionController` before one direct viewer-event delivery, with no forwarding route back through `RunController`.
- `REQ-EXEC-009`: the typed command/event protocol shall remain the canonical planned-public execution boundary shared by the headless execution API, QML shell client, runtime snapshot, and worker. Unified workflow interfaces, remote transport, and permissioned-agent operations are separate planned protocol consumers under `REQ-NODE-036`, `REQ-EXEC-020`, and `REQ-EXEC-022`; this pointer does not claim those consumers are implemented.

## Scheduling and Failure Handling
- `REQ-EXEC-004`: The worker shall replace control queues, Start special cases, failure-edge routing, and execution-target chains with dependency traversal over enabled data edges; each node shall be scheduled at most once per requested solution even when access matching invokes its plugin repeatedly.
- `REQ-EXEC-005`: The compiler and worker shall propagate ordered DataTrees through enabled edges and execute the fixed merge, modifier, access-matching, plugin-call, atomic-aggregation, output-modifier pipeline defined by `REQ-NODE-041` through `REQ-NODE-043`.
- `REQ-EXEC-006`: Runtime failures shall emit structured root errors and traceback payloads that preserve authored node IDs for diagnostics and shell focus. Failed input shall block dependents without cascade errors, while independent branches continue. Reproducible debug bundles are a separate planned diagnostic scope under `REQ-EXEC-019`; they do not widen this requirement.
- `REQ-EXEC-007`: the worker shall emit run/node lifecycle events covering start, state transitions, completion, settlement, failure, stop, logs, and protocol errors; when available, `node_started` and `node_settled` shall also carry additive `started_at_epoch_ms` and `elapsed_ms` metadata around actual plugin execution time without breaking shell-side fallback timing on emitters that omit those fields. Event capture for reproducible debug bundles is a separate planned scope under `REQ-EXEC-019`; it does not widen this requirement or its existing proof.
- `REQ-EXEC-008`: stop requests shall cancel active subprocess-backed execution safely instead of leaving orphaned child processes running.
- `REQ-EXEC-014`: The execution command protocol shall support Run and Run Selected only. Before either explicit command assembles or dispatches a runtime snapshot, the shell shall synchronize any valid pending authoring edit that the command is defined to consume; failed synchronization shall dispatch no execution command and leave the graph without partial mutation. Run targets every active node; Run Selected carries selected active target IDs and expands their enabled upstream dependency closure. Explicitly selected isolated nodes run, while unrelated branches remain excluded. The protocol shall contain no upstream-chain mode or selected-run output seeds.
- `REQ-EXEC-023`: App preference `solution.default_mode` shall default to `auto`. Every opened workspace shall initialize its runtime-only mode from that preference; Auto shall evaluate immediately on project open and after execution-affecting graph or property changes. Manual/Pause changes only the live workspace. An active run finishes against its snapshot, affected outputs become stale, and qualifying edits coalesce into one pending rerun. When an Apply is consumed as part of explicit Run or Run Selected dispatch, its model change shall not schedule a duplicate Auto rerun. Stop or infrastructure failure cancels pending work. All active nodes are eligible, while disabled edges and Trigger nodes bound propagation.

## Managed Output Transport
- `REQ-EXEC-010`: runtime snapshots and queue payloads shall serialize `RuntimeArtifactRef` values as structured `artifact_ref` payloads so stored outputs can cross the execution boundary as `saved://...` or `temp://...` handles instead of inline blobs.
- `REQ-EXEC-011`: execution contexts and downstream file-backed integrations shall resolve saved and temporary artifact refs against runtime-snapshot and project artifact metadata during the same run.
- `REQ-EXEC-012`: `Process Run` stored mode shall write stdout/stderr transcript outputs under the owning node's `tmp/out/generated/process_run/` lifecycle, emit temporary refs on success, and remove temporary transcript files plus metadata on non-zero failure or cancellation.
- `REQ-EXEC-013`: the execution engine shall expose a registry-driven runtime/viewer backend contract: `ViewerBackendRegistry`, `ViewerSessionService`, and later `RuntimeBackendSpec` descriptors publish `backend_id`, typed `transport`, `transport_revision`, and explicit `live_open_status` / `live_open_blocker` fields through queue-safe viewer protocol payloads, while concrete backends such as the DPF implementation materialize session-scoped temp transport bundles from worker-local state instead of pushing raw PyVista or VTK objects across the boundary.
- `REQ-EXEC-015`: The existing shell-owned output cache shall remain session-only and record enough per-node/output state to distinguish never-run, empty, stale, and current values for bounded UI previews. It shall not seed Run Selected, satisfy missing dependencies, become a second scheduler truth, or serialize into `.cxproj`; durable solution snapshots remain a separate planned scope under `REQ-EXEC-017` and `REQ-PERSIST-026`.
- `REQ-EXEC-016`: the worker shall own `corex.scene_bundle.v1` prepared scenes and exact CAD objects behind runtime handles, key workspace cache manifests by source SHA-256, importer version, and normalized unit settings, reject malformed/non-JSON scene metadata, detect source changes during import, and expose capability-based materialization and query results without transferring live VTK, PyVista, OCP, or DPF objects to the UI.
- `REQ-EXEC-024`: Internal port results shall be `pending`, `value(DataTree)`, `empty`, or `failed(root errors)`. Empty or unresolved required input shall skip plugin execution, settle and propagate empty, and shall not fail the run; empty optional input shall use omission/default. Internal node helpers may signal that mandatory data is not ready so the worker settles empty with a warning. The engine shall detect cycles before execution.
- `REQ-EXEC-025`: Runtime snapshots shall carry structured ordered edges with `enabled` and `input_order`, not endpoint tuple/set summaries. Disabled edges remain authored but contribute no dependency, path, or item, and all plugin calls within one node remain sequential.
- `REQ-EXEC-026`: Trigger publication shall be runtime-only. A click shall publish the newest settled input, empty, or root failure and rerun downstream only to the next Trigger boundary; stale input shall refresh upstream first, unconnected Trigger shall publish `True`, and Stop/infrastructure failure shall cancel a pending capture without replacing the old publication. If and Stream Gate shall propagate only their selected Tree value; inactive Stream Gate outputs are explicit EMPTY.
- `REQ-EXEC-027`: Before Python Script execution, the worker shall independently resolve the applied decorator source through the same registry instance-spec path used by graph and snapshot assembly. It shall execute only after successful resolution, preserve process-isolated timeout handling and sanitized `<script>` tracebacks, and use the resolved ports for input/output validation.
- `REQ-EXEC-029`: Workflow execution shall select one backend for the whole workflow. Explicit process, trusted, or auto policy shall ignore project and app Python defaults; explicit external policy shall use its own executable or, when pathless, fall back only to the project workflow override. Without explicit policy, a non-empty project override shall select external Python; only shell dispatch with an empty project override may inject app preference `python_runtime.default_executable`; both stored paths blank shall select the built-in process-isolated runtime, with no PATH or environment discovery. Selection shall read normalized text first and validate the final non-empty external path exactly once with bounded malformed-path errors. A new, dead, or switched external worker shall pass the bounded `ea_node_editor.execution.stdio_worker` import preflight before run reservation; a live same-path worker shall be reused without re-probe, restart, or generation advance; unsafe switches shall retain the existing viewer guard. A post-preflight process-launch failure shall release the reserved run, accept no new physical/catalog generation, emit a bounded actionable error, and permit the next valid run to recover; a failed switch need not restore an already retired prior worker. Registry, catalog, plugin, and protocol agreement shall remain in the existing post-launch handshake. The app-default executable shall never be copied into project metadata, runtime snapshots, protocol fields, graph/node records, or per-node/plugin settings; the intentional project Workflow Override remains project metadata.

## Planned Execution Contracts
- `REQ-EXEC-017`: The execution engine shall own solution identity, immutable records, current/expired facts, prepared reuse decisions, and exact downstream invalidation. Solution identity shall derive from the normalized workflow interface, executable dependency closure, relevant authored values, input and artifact provenance, implementation and toolchain versions, and execution policy. Runs shall recompute only invalidated dependency closure, report every reuse, recomputation, skip, and block reason, and never treat the shell's session-only presentation cache as scheduler or durable-snapshot truth. Evidence crosswalk: `SYN-OPP-0002`.
- `REQ-EXEC-018`: The execution engine shall emit a planned dependency and provenance report for every prepared run that relates authored nodes and interfaces to resolved dependencies, source definitions and versions, inputs, artifacts, snapshot decisions, execution location, and produced results; the report shall explain why each node ran, reused a result, skipped, or became blocked and shall remain queryable without mutating execution state. The report shall consume the accepted interface and snapshot contracts from `REQ-NODE-036`, `REQ-EXEC-017`, and `REQ-PERSIST-026`. Evidence crosswalk: `SYN-OPP-0004`.
- `REQ-EXEC-019`: The execution engine shall export planned reproducible debug bundles through a deterministic manifest that can include the normalized workflow snapshot, prepared plan, bounded protocol events and logs, structured failures, dependency and provenance reports, and environment, plugin, backend, toolchain, and artifact descriptors; an explicit redaction policy shall exclude credentials and secrets by default, identify every omission or transformation, and fail closed when required redaction cannot be verified. Evidence crosswalk: `SYN-OPP-0005`.
- `REQ-EXEC-020`: The execution engine shall support planned secure remote execution through the canonical typed command/event boundary with explicit endpoint handshake, capability and protocol negotiation, authenticated trust, encrypted transport, idempotent run identity, bounded retry, timeout and cancellation semantics, integrity-checked artifact transfer, and end-to-end provenance; local and remote execution shall remain explicit choices and an unavailable remote endpoint shall not cause silent local fallback. Acceptance of this contract is a prerequisite for permissioned agent orchestration under `REQ-ARCH-020` and `REQ-EXEC-022`. Evidence crosswalk: `SYN-OPP-0006`.
- `REQ-EXEC-021`: The execution engine shall run planned solver-neutral FEA jobs as validated process-stage lifecycles through a selected integration adapter; it shall preflight capabilities, produce a deterministic job manifest, report stage state and diagnostics, preserve neutral and solver-specific artifact provenance, and define safe retry or resume boundaries without importing solver objects into the canonical execution protocol. Evidence crosswalk: `SYN-OPP-0007`.
- `REQ-EXEC-022`: The execution engine shall run planned permissioned-agent plans as typed, auditable steps with resolved capability grants, approval state, budgets, timeouts, cancellation, idempotency, proposed-versus-completed effects, and provenance; unapproved graph mutations or external side effects shall be rejected before dispatch. Implementation shall remain blocked until `REQ-NODE-036`, `REQ-EXEC-017`, `REQ-EXEC-018`, `REQ-EXEC-020`, and `REQ-PERSIST-026` are accepted. Evidence crosswalk: `SYN-OPP-0008`.
- `REQ-EXEC-028`: Every runtime start command shall carry bounded `PluginBundleRef` values, `plugin_fingerprint`, complete registry-contract fingerprint, and accepted add-on runtime configuration. Public plugin source shall be copied only after static validation into an immutable content-addressed generation under an approved root. The process worker, including the existing workflow-level external Python stdio client when selected, shall reconstruct the accepted registry, re-hash exact generation members before import, load required functions lazily under digest-derived module names, reject path escapes, missing agreement, stale generations, and digest mismatches, and never import unused plugins or mutable author source. Trusted in-process execution shall accept only independently attested internal function generations and shall reject external public function references before client state changes. `CorexRuntime.replace_registry(registry)` shall retire incompatible process/external clients, worker generations, viewers, and preparation caches when the accepted contract changes, while author-source edits remain invisible until the next successful reload. This requirement does not implement a plugin-selectable external runner, per-plugin interpreter, or dependency environment.

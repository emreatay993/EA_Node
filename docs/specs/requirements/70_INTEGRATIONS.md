# Integrations Requirements

## Built-In Integration Families
- `REQ-INT-001`: Core built-ins shall remain available without optional third-party integration dependencies.
- `REQ-INT-002`: The repo shall ship built-in integration families for spreadsheet, file I/O, email, process execution, and optional domain-specific integrations through the shared registry/bootstrap path.
- `REQ-INT-003`: Spreadsheet integrations shall cover CSV/XLSX read/write workflows with dependency-gated behavior.
- `REQ-INT-004`: File integrations shall cover text/JSON read/write workflows with path-oriented node contracts.
- `REQ-INT-005`: Email integrations shall cover SMTP/TLS/auth send workflows with explicit configuration.
- `REQ-INT-007`: Built-in integration nodes shall stay grouped under the integrations catalog/bootstrap surface rather than ad-hoc registration paths.
- `REQ-INT-011`: built-in add-on integrations shall flow through the generic add-on catalog and shell-manager contract: each add-on publishes stable id, name, version, category, dependency, and availability facts plus runtime/toolchain/artifact/surface capability descriptors and exactly one apply policy (`hot_apply` or `restart_required`), while shell open-manager requests and missing-node ownership resolve against add-on ids instead of ad hoc plugin package names.
- `REQ-INT-013`: File I/O integrations shall include the passive `io.folder_explorer` Classic Explorer node backed by a UI-independent real-filesystem service for listing, breadcrumb assembly, filtering, sorting, path-copy formatting, explicit-confirmation file mutations, and Path Pointer handoff, while keeping graph mutations behind existing graph command services.
- `REQ-INT-014`: the COREX Excalidraw web host integration shall be a built-in, local/offline, COREX-owned real editor layer: `PyQt6-WebEngine` is a required runtime dependency for normal desktop source and packaged app sessions, the editor bundle is built from repo-local Vite/React source pinned to `@excalidraw/excalidraw@0.18.1`, unsupported desktop WebEngine environments degrade through explicit unavailable-authoring projections, headless Corex sessions keep the board as persisted passive data without browser execution, packaged assets under `ea_node_editor/web_assets/excalidraw_host/` are the only host content source, Python/JavaScript exchange stays behind the validated `WebSurfaceBridge`, managed image imports and artifact-backed previews flow through `ProjectArtifactStore`, and the scope shall not open external browsers, remote rooms, collaboration services, execution-worker web semantics, or arbitrary third-party web UI registration.
- `REQ-INT-015`: Plugin and add-on integrations shall define public `RuntimeBackendSpec`, `ToolchainSpec`, `ArtifactDescriptor`, and `SurfaceCapabilitySpec` contracts before compiled Rust, C++, or other foreign-language nodes are allowed to participate in runtime loading; these contracts may declare backend adapters, optional library/compiler requirements, version checks, and prepared artifacts, but they do not authorize native build execution. Remote endpoint trust and execution capability negotiation are separate planned scopes under `REQ-INT-018` and `REQ-EXEC-020`; they do not widen this requirement or its existing proof.
- `REQ-INT-016`: generic Chromium/Qt WebEngine consumers shall route user-provided URL and local HTML content through the shared navigation-normalization layer and the bridge-free `web_page` surface contract: `file`, `http`, and `https` targets are normalized to a safe load URL while unsupported schemes and embedded credentials are rejected; local files and relative assets load without internet access; WebEngine cookies, cache, session storage, credentials, and page content remain outside project `.cxproj` persistence; and future trusted web applications must define a separate bridge contract instead of inheriting the Excalidraw `WebSurfaceBridge`.
- `REQ-INT-017`: the solver-neutral viewer integration shall support STEP, IGES, BREP, STL, legacy VTK, VTU, VTM, VTKHDF, Exodus, and XDMF through PyVista/VTK plus pinned `cadquery-ocp-novtk==7.9.3.1.1`; preserve external source paths and source coordinates; require explicit units when absent; convert overlay display units without modifying source data; exclude Ansys DPF from every application package profile; and carry OCP/OCCT license, source/build, and dynamically linked library information in viewer packages.
- `REQ-INT-020`: Built-in SSH command, script, upload, and download operations shall use required `paramiko>=4,<5` in source and every package profile. Each operation shall create and close its own client, load system known-host files, use `RejectPolicy`, and never auto-trust/write host keys or fall back to system `ssh`/`scp`. Authentication shall support DPAPI-protected password or key passphrase, a private-key path, and exact OpenSSH/Pageant selection; the per-agent selection may use the version-pinned Paramiko 4 internals because its public API cannot distinguish them. Command/script execution shall use 30-second connect/banner/auth/channel timeouts, a 30-second keepalive, stop callbacks, no PTY/stdin, UTF-8 replacement, 16 MiB stdout/stderr caps, structured nonzero outputs, and per-run cleanup. Script execution shall cap source at 4 MiB, normalize line endings, use the declared Bash/sh/Python/Perl interpreter or a required Custom shebang, stage under a unique mode-0700 `/tmp/.corex-run-ssh-script-*` directory, and remove it in `finally`. SFTP shall recurse through directory contents, require a directory destination for multiple sources or directory sources, skip symlinks with warnings, reject destination escapes, use temporary-file atomic commit, honor no-replace or overwrite, and count only committed regular files and bytes.
- `REQ-INT-022`: The dependency-gated Mechanical add-on shall publish exactly `mechanical.open_model`, `mechanical.search_tree`, `mechanical.fea_table`, `mechanical.camera_views`, `mechanical.export_image`, `mechanical.run_script`, `mechanical.apdl_snippet`, and `mechanical.save_model` under `FEA > ANSYS > Mechanical`, with the typed ports, Item/List/Tree access, section groups, defaults, fresh-run ownership, 2026 R1 minimum, later-release capability handshake, eleven background Search meanings, explicit result-evaluation-without-solve boundary, camera/image DataTree ordering, scoped Script and owned load-step Snippet behavior, and native source-family Save/publication limits documented in the [Mechanical Catalogue guide](../../MECHANICAL_CATALOGUE.md). The repository shall ship the three deterministic blank-path `.cxproj` workflows linked there; fixture paths are injected only after load through validated graph mutation, and transient handles/catalogues/picker identities never persist in the authored examples.

## Planned Integration Contracts
- `REQ-INT-018`: Integrations shall expose planned `RemoteEndpointDescriptor` and `ExecutionCapabilityManifest` contracts that identify endpoint provenance, protocol and contract versions, available runtimes and resources, artifact-transfer limits, trust and authentication requirements, and health without embedding credential values; endpoint adapters shall validate compatibility and policy before dispatch and shall not authorize untrusted code or capabilities merely because an endpoint advertises them. Evidence crosswalk: `SYN-OPP-0006`.
- `REQ-INT-019`: Solver integrations shall expose a planned adapter contract that maps solver-neutral FEA process stages and jobs to solver-specific toolchains or endpoints, publishes supported features, versions, licenses, resource requirements, and limitations, rejects unsupported mappings explicitly, and returns neutral result and artifact descriptors with solver-specific diagnostics and provenance. This requirement shall not widen the delivered neutral viewer scope in `REQ-INT-017`. Evidence crosswalk: `SYN-OPP-0007`.
- `REQ-INT-021`: Public loose plugins shall be single root-level `.py` files discovered statically and shall use the default icon. Multi-file or custom-asset plugins shall use deterministic `.cxpkg` schema 2 with exactly `schema_version`, `name`, `version`, `modules`, `sources`, `assets`, and generated `nodes` fields; canonical relative `/` paths; SHA-256 for every source and asset; root-level Python sources; and only `.svg`, `.png`, `.jpg`, or `.jpeg` assets. Limits shall be 64 KiB for the manifest, 256 KiB per Python source, 4 MiB per asset, 128 total members, and 16 MiB total expanded content. Export shall canonicalize manifest JSON, sort members, normalize archive timestamps, and derive the bundle digest from the canonical manifest plus sorted exact member bytes. Import shall reject public-package schema 1, unknown or missing fields, unknown or undeclared members, hash mismatch, encrypted members, symlinks/hard links, absolute or traversing paths, backslashes, dot segments, Windows case-insensitive duplicates/reserved names, nested Python packages, unsupported assets, and all limit violations without partial installation. Package import, export, validation, and local reload shall execute no public source. Reload shall parse all active sources into one fresh candidate registry; validate every open workspace, incident wire, and saved value; materialize immutable generations only after validation; atomically replace package files and ordered registry consumers; retire affected process/external workflow workers, viewers, and preparation caches; and restore every file and consumer on failure. Missing bundled absolute imports shall keep nodes visible but locked with the exact `<module> is not included in this COREX bundle.` message. Entry-point loading, `ea_node_editor.plugins`, dependency installation, environment mutation, watchers, and plugin-level interpreter or external-runner selection shall remain absent; the existing workflow-level external Python client is a separate execution setting and is not removed by this requirement. See the [Novice Plugin Authoring Guide](../../PLUGIN_AUTHORING_GUIDE.md) and [Legacy Plugin Migration Guide](../../PLUGIN_MIGRATION_GUIDE.md).

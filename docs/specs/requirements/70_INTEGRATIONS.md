# Integrations Requirements

## Built-In Integration Families
- `REQ-INT-001`: Core built-ins shall remain available without optional third-party integration dependencies.
- `REQ-INT-002`: The repo shall ship built-in integration families for spreadsheet, file I/O, email, process execution, and optional domain-specific integrations through the shared registry/bootstrap path.
- `REQ-INT-003`: Spreadsheet integrations shall cover CSV/XLSX read/write workflows with dependency-gated behavior.
- `REQ-INT-004`: File integrations shall cover text/JSON read/write workflows with path-oriented node contracts.
- `REQ-INT-005`: Email integrations shall cover SMTP/TLS/auth send workflows with explicit configuration.
- `REQ-INT-007`: Built-in integration nodes shall stay grouped under the integrations catalog/bootstrap surface rather than ad-hoc registration paths.
- `REQ-INT-008`: The PyDPF viewer integration surface shall treat `ansys-dpf-core` as the analysis backend and `pyvista`, `pyvistaqt`, plus `vtk` as optional viewer extras; shipped built-ins include foundational helper and workflow nodes `dpf.result_file`, `dpf.model`, `dpf.scoping.mesh`, `dpf.scoping.time`, `dpf.mesh_extract`, and `dpf.export`, the foundational operator-backed nodes `dpf.result_field` and `dpf.field_ops`, generated `dpf.op.*` operator wrappers, and `dpf.viewer`; the retained nested-category proof continues to cover the earlier `("Ansys DPF", "Compute")` and `("Ansys DPF", "Viewer")` surface, while the shipped Ansys DPF catalog taxonomy now uses `category_path` with `("Ansys DPF", "Inputs")`, `("Ansys DPF", "Workflow")`, `("Ansys DPF", "Helpers", ...)`, `("Ansys DPF", "Operators", ...)`, and `("Ansys DPF", "Viewer")` as the visible root families and leaves only `("Ansys DPF", "Advanced", "Raw API Mirror")` deferred; `dpf.viewer` is the first concrete `backend_id` implementation of the generic execution-backend and shell-binder framework (`dpf_embedded`) and is expressed through `RuntimeBackendSpec`, `ToolchainSpec`, `ArtifactDescriptor`, and `SurfaceCapabilitySpec` records, while repo-local `.rst` / `.rth` fixtures under `tests/ansys_dpf_core/example_outputs/` remain the authoritative smoke inputs for packet-owned verification.
- `REQ-INT-009`: The operator-backed Ansys DPF rollout surface shall keep `ansys-dpf-core>=0.16,<0.17` optional, register shipped DPF descriptors through the descriptor/add-on catalog when the backend is available, and apply a version-aware plugin lifecycle. On an exact catalog/runtime version match it shall load the committed schema-1 deterministic operator catalog without operator construction or live discovery; for another supported `0.16.x` patch or an invalid catalog it shall warn once and discover live in memory; if live discovery fails it shall omit only generated raw-operator mirrors; it shall never create an automatic writable user cache; and viewer/full package preflight shall fail when the build-environment DPF version and committed catalog differ. The surface shall continue to normalize operator metadata and generated-port semantics into stable registry/runtime descriptors, publish generated operator and helper descriptors with source-family provenance, route operator-backed compute nodes through the generic DPF runtime adapter, materialize helper-provided generic object handles, preserve reopened `dpf.*` nodes as locked unavailable-add-on surfaces when the add-on/backend is unavailable, and defer the broad non-operator `ansys.dpf.core` reflection surface under `Ansys DPF > Advanced > Raw API Mirror`.
- `REQ-INT-010`: `dpf.viewer` content fullscreen shall retarget the existing native viewer widget and overlay host into the shell `contentFullscreenViewerViewport` when live data is available, restore the same widget to the node viewport on close, workspace switch, or node deletion, and keep blocked or rerun-required viewer states as explicit shell projections without creating a second viewer widget for the same `(workspace_id, node_id)`.
- `REQ-INT-011`: built-in add-on integrations shall flow through the generic add-on catalog and shell-manager contract: each add-on publishes stable id, name, version, category, dependency, and availability facts plus runtime/toolchain/artifact/surface capability descriptors and exactly one apply policy (`hot_apply` or `restart_required`), while shell open-manager requests and missing-node ownership resolve against add-on ids instead of ad hoc plugin package names.
- `REQ-INT-012`: `ANSYS DPF` shall ship as the first repo-local `hot_apply` add-on under `ea_node_editor.addons.ansys_dpf`, remain optional at startup, and participate in registry, runtime, `RuntimeBackendSpec`, and viewer rebuild. The guarded shell transaction shall refuse disabling it while an open graph still requires a DPF node; otherwise disabling and re-enabling shall rebuild runtime/viewer ownership without a full app restart, while projects opened with the add-on unavailable retain locked unavailable-add-on projections.
- `REQ-INT-013`: File I/O integrations shall include the passive `io.folder_explorer` Classic Explorer node backed by a UI-independent real-filesystem service for listing, breadcrumb assembly, filtering, sorting, path-copy formatting, explicit-confirmation file mutations, and Path Pointer handoff, while keeping graph mutations behind existing graph command services.
- `REQ-INT-014`: the COREX Excalidraw web host integration shall be a built-in, local/offline, COREX-owned real editor layer: `PyQt6-WebEngine` is a required runtime dependency for normal desktop source and packaged app sessions, the editor bundle is built from repo-local Vite/React source pinned to `@excalidraw/excalidraw@0.18.1`, unsupported desktop WebEngine environments degrade through explicit unavailable-authoring projections, headless Corex sessions keep the board as persisted passive data without browser execution, packaged assets under `ea_node_editor/web_assets/excalidraw_host/` are the only host content source, Python/JavaScript exchange stays behind the validated `WebSurfaceBridge`, managed image imports and artifact-backed previews flow through `ProjectArtifactStore`, and the scope shall not open external browsers, remote rooms, collaboration services, execution-worker web semantics, or arbitrary third-party web UI registration.
- `REQ-INT-015`: Plugin and add-on integrations shall define public `RuntimeBackendSpec`, `ToolchainSpec`, `ArtifactDescriptor`, and `SurfaceCapabilitySpec` contracts before compiled Rust, C++, or other foreign-language nodes are allowed to participate in runtime loading; these contracts may declare backend adapters, optional library/compiler requirements, version checks, and prepared artifacts, but they do not authorize native build execution. Remote endpoint trust and execution capability negotiation are separate planned scopes under `REQ-INT-018` and `REQ-EXEC-020`; they do not widen this requirement or its existing proof.
- `REQ-INT-016`: generic Chromium/Qt WebEngine consumers shall route user-provided URL and local HTML content through the shared navigation-normalization layer and the bridge-free `web_page` surface contract: `file`, `http`, and `https` targets are normalized to a safe load URL while unsupported schemes and embedded credentials are rejected; local files and relative assets load without internet access; WebEngine cookies, cache, session storage, credentials, and page content remain outside project `.cxproj` persistence; and future trusted web applications must define a separate bridge contract instead of inheriting the Excalidraw `WebSurfaceBridge`.
- `REQ-INT-017`: the solver-neutral viewer integration shall support STEP, IGES, BREP, STL, legacy VTK, VTU, VTM, VTKHDF, Exodus, and XDMF through PyVista/VTK plus pinned `cadquery-ocp-novtk==7.9.3.1.1`; preserve external source paths and source coordinates; require explicit units when absent; convert overlay display units without modifying source data; keep Ansys DPF optional outside the `full` package profile; and carry OCP/OCCT license, source/build, and dynamically linked library information in viewer packages.
- `REQ-INT-020`: Built-in SSH command, script, upload, and download operations shall use required `paramiko>=4,<5` in source and every package profile. Each operation shall create and close its own client, load system known-host files, use `RejectPolicy`, and never auto-trust/write host keys or fall back to system `ssh`/`scp`. Authentication shall support DPAPI-protected password or key passphrase, a private-key path, and exact OpenSSH/Pageant selection; the per-agent selection may use the version-pinned Paramiko 4 internals because its public API cannot distinguish them. Command/script execution shall use 30-second connect/banner/auth/channel timeouts, a 30-second keepalive, stop callbacks, no PTY/stdin, UTF-8 replacement, 16 MiB stdout/stderr caps, structured nonzero outputs, and per-run cleanup. Script execution shall cap source at 4 MiB, normalize line endings, use the declared Bash/sh/Python/Perl interpreter or a required Custom shebang, stage under a unique mode-0700 `/tmp/.corex-run-ssh-script-*` directory, and remove it in `finally`. SFTP shall recurse through directory contents, require a directory destination for multiple sources or directory sources, skip symlinks with warnings, reject destination escapes, use temporary-file atomic commit, honor no-replace or overwrite, and count only committed regular files and bytes.

## Planned Integration Contracts
- `REQ-INT-018`: Integrations shall expose planned `RemoteEndpointDescriptor` and `ExecutionCapabilityManifest` contracts that identify endpoint provenance, protocol and contract versions, available runtimes and resources, artifact-transfer limits, trust and authentication requirements, and health without embedding credential values; endpoint adapters shall validate compatibility and policy before dispatch and shall not authorize untrusted code or capabilities merely because an endpoint advertises them. Evidence crosswalk: `SYN-OPP-0006`.
- `REQ-INT-019`: Solver integrations shall expose a planned adapter contract that maps solver-neutral FEA process stages and jobs to solver-specific toolchains or endpoints, publishes supported features, versions, licenses, resource requirements, and limitations, rejects unsupported mappings explicitly, and returns neutral result and artifact descriptors with solver-specific diagnostics and provenance. This requirement shall not widen the delivered neutral viewer scope in `REQ-INT-017`. Evidence crosswalk: `SYN-OPP-0007`.
- `REQ-INT-021`: Public loose plugins shall be single root-level `.py` files discovered statically and shall use the default icon. Multi-file or custom-asset plugins shall use deterministic `.cxpkg` schema 2 with exactly `schema_version`, `name`, `version`, `modules`, `sources`, `assets`, and generated `nodes` fields; canonical relative `/` paths; SHA-256 for every source and asset; root-level Python sources; and only `.svg`, `.png`, `.jpg`, or `.jpeg` assets. Limits shall be 64 KiB for the manifest, 256 KiB per Python source, 4 MiB per asset, 128 total members, and 16 MiB total expanded content. Export shall canonicalize manifest JSON, sort members, normalize archive timestamps, and derive the bundle digest from the canonical manifest plus sorted exact member bytes. Import shall reject public-package schema 1, unknown or missing fields, unknown or undeclared members, hash mismatch, encrypted members, symlinks/hard links, absolute or traversing paths, backslashes, dot segments, Windows case-insensitive duplicates/reserved names, nested Python packages, unsupported assets, and all limit violations without partial installation. This public `.cxpkg` schema-1 rejection shall not alter the separate trusted DPF operator-catalog schema 1 required by `REQ-INT-009`. Package import, export, validation, and local reload shall execute no public source. Reload shall parse all active sources into one fresh candidate registry; validate every open workspace, incident wire, and saved value; materialize immutable generations only after validation; atomically replace package files and ordered registry consumers; retire affected process/external workflow workers, viewers, and preparation caches; and restore every file and consumer on failure. Missing bundled absolute imports shall keep nodes visible but locked with the exact `<module> is not included in this COREX bundle.` message. Entry-point loading, `ea_node_editor.plugins`, dependency installation, environment mutation, watchers, and plugin-level interpreter or external-runner selection shall remain absent; the existing workflow-level external Python client is a separate execution setting and is not removed by this requirement. See the [Novice Plugin Authoring Guide](../../PLUGIN_AUTHORING_GUIDE.md) and [Legacy Plugin Migration Guide](../../PLUGIN_MIGRATION_GUIDE.md).
